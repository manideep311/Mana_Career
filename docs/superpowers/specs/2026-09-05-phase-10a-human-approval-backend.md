# Phase 10a — Human approval workflow (backend) design addendum

> Delta over master `2026-08-30-mana-career-design.md` §4.2/§4.6/§4.7/§5.3/§6.2/§9 (roadmap row 10). Frontend (the 7-step Builder UI + approval card) is Phase 10b, its own cycle. This is the most novel phase of the project so far — it introduces LangGraph's interrupt/resume mechanism, which nothing built in Phases 7–9 uses — so this addendum documents the exact API surface verified against the installed `langgraph==1.2.11`, not assumed from the master's prose.

## 0. Goal (roadmap row 10)

Close the loop from a drafted résumé + cover letter + email to an actual, human-approved, sent application: `application_prep` (deterministic assembly + hash) → `human_approval` (pause the graph, wait for a person) → `email_external_action` (assert approved + hash match, send via a sandboxed `EmailSender`, audit). "Done when": Prepare Application → review → Approve & Send → "sent at 10:42 AM" + audit log; no send without an approved row; a hash mismatch halts.

## 1. Rulings made before any task was planned

**R1 — `human_approval` must be a RAW node, not `guard()`-wrapped.** Verified directly against the installed `langgraph==1.2.11`: `interrupt()` raises `langgraph.errors.GraphInterrupt`, and `GraphInterrupt.__mro__` is `(GraphInterrupt, GraphBubbleUp, Exception, BaseException, object)` — it **is** an `Exception` subclass. `budget.guard()`'s node wrapper has a bare `except Exception as exc:` around the node call ([budget.py:107-109](../../../backend/app/domain/agents/budget.py)) that would catch a `GraphInterrupt` and mis-report the intentional pause as a fatal node error, breaking the entire mechanism. Fix: register `human_approval` **raw** in `graph.py`, exactly like `supervisor`/`halted` are today (per `graph.py`'s own docstring — "the supervisor and halted nodes are wired raw... the worker nodes are wrapped in guard()"). This also means `human_approval` consumes no LLM/tool budget and gets no automatic `step_log` entry — appropriate, since it does no real work.

**R2 — `guard()` gets one defensive line: let `GraphBubbleUp` through.** Even with R1, add `except GraphBubbleUp: raise` as the *first* except clause in `guard()`'s node-call try/except, before the generic `except Exception`. `GraphBubbleUp` is LangGraph's own base class for control-flow exceptions designed to propagate through arbitrary call stacks unimpeded (`interrupt`'s and other primitives' exceptions all derive from it) — no node this phase calls `interrupt()` from inside a `guard()`-wrapped node, so this never fires today, but it is cheap, correct, and forward-compatible if a later phase ever nests interrupt-like behavior inside a bounded node. `app/domain/agents/budget.py` is the only file this touches.

**R3 — `interrupt()`'s re-execution semantic shapes `human_approval`'s body.** Verified directly (`interrupt.__doc__`): "the graph resumes from the start of the node, **re-executing** all logic." Everything in `human_approval` before its `interrupt(...)` call runs twice (once to pause, once on resume) — it must be a pure read. Design: `application_prep` (a normal, once-only, `guard()`-wrapped node) does ALL the writing — it creates the `applications` row and the `approval_requests` row (snapshot + hash) — and stores `state["application_id"]` / `state["approval_request_id"]`. `human_approval` only re-reads the `approval_requests` row by the id already in state (a harmless repeat on resume) to build the interrupt's payload, then calls `interrupt({"approval_id": approval_id})` and, on resume, reads the returned `{"decision": ..., "note": ...}` dict — matching a plain `dict[str, Any]` return type from `interrupt()`, not a typed object (verified: `interrupt(value: Any) -> Any`).

**R4 — the interrupt's payload is a bare id, not the full snapshot.** Keeping `interrupt()`'s value small (`{"approval_id": "<uuid>"}`) avoids duplicating the potentially-large `payload_snapshot` (cover letter + email body) inside the LangGraph checkpoint blob, which gets serialized on every step. The frontend (Phase 10b) fetches the full snapshot via `GET /approvals/{id}` once it learns the id from the SSE `approval` event — one extra round trip, a table's worth of durability (a missed SSE frame doesn't lose the payload; `GET /approvals?status=pending` finds it again).

**R5 — resuming needs a second worker task, not a second call to `run_agent`.** `run_agent` (Phase 7a) always builds a **fresh** `ManaState` init dict and calls `graph.astream(init, config=gcfg, ...)` ([agent.py:94-109](../../../backend/app/worker/tasks/agent.py)) — correct for a brand-new run, wrong for resuming a paused thread, which must call `graph.astream(Command(resume={...}), config=gcfg, ...)` instead (verified: `Command(*, resume: dict[str, Any] | Any | None = None, ...)`). Both entry points share everything *after* building `deps`/`graph`/`gcfg` — the astream-drain loop, interrupt detection, finalize/error handling — so that shared logic is extracted into one `_drive(...)` helper Task 8 writes once; `run_agent` and the new `resume_agent` become thin wrappers that build a different graph *input* and call it.

**R6 — detecting a pause vs. a real finish.** After the astream loop ends (for either entry point), `snap = await graph.aget_state(gcfg)`. Verified fields on `StateSnapshot` (`langgraph.types`): `values, next, config, metadata, created_at, parent_config, tasks, interrupts`. `snap.interrupts` (a tuple) is non-empty exactly when the graph is paused mid-run. When it is: do **not** call `AgentService.finalize()` (which stamps `ended_at`, implying the run ended) — instead call a new `AgentService.mark_awaiting_approval(session_id)` (status only, no `ended_at`), publish `{"event": "approval", "approval_id": ...}` then `{"event": "done", "status": "awaiting_approval", "totals": {...}}` (so the relay's existing `if payload.get("event") == "done": return` closes the SSE connection cleanly instead of idling to its 300s cap — reusing the existing single-attempt frontend SSE consumer pattern from Phase 8b/9 unchanged). When `snap.interrupts` is empty, the existing finalize/done logic runs exactly as today.

**R7 — `ManaState.status` gains `"awaiting_approval"`; the DB column already allows it.** `ai_sessions.status`'s CHECK constraint (migration from Phase 7a) is `status in ('idle','running','awaiting_approval','completed','rejected','halted','error')` — **already includes it**, verified directly in `app/models/ai.py`. Only the Python-level `ManaState.status` `Literal` (currently missing it) needs widening. No new migration for this.

**R8 — no reject→revise loop this phase.** The master spec's fuller vision has reject looping back to tailoring/the letter with feedback, capped at one loop (`revise_count`). The roadmap row's own "done when" bar is narrower — prepare → review → approve → send — and does not require revise to work. Building the feedback-loop prompt engineering now, unvalidated by any concrete acceptance bar, is scope creep with real design risk (what feedback text, which node re-enters, does `cover_letter`/`resume_tailoring` need a new "previous rejection" input). Ruling: `reject` is terminal this phase — `human_approval` returns `{"status": "rejected", ...}` on a reject decision, full stop. `revise_count` stays in `ManaState`, unused, exactly as Phase 7a left it, for a later phase to pick up.

**R9 — no "edits" reconfirm flow this phase.** The master's `POST /approvals/{id}` accepts an optional `edits` field that recomputes the payload and re-shows it for a second confirmation. Phase 10a's `ApprovalDecisionIn` schema omits `edits` entirely (not merely ignores it — `extra="forbid"` on the schema makes supplying it a 422). A later phase can add it without breaking this one's contract (adding an optional field is backward compatible).

**R10 — `/applications`'s scope this phase is two endpoints, not the full resource.** Phase 11 ("Application tracker") owns the full CRUD + list + notes + timeline + Kanban surface. Phase 10a builds only what "Prepare Application → review → Approve & Send" needs: `POST /applications {job_id}` → 202 `{run_id, session_id}` (starts the `prepare_application` goal — the first real trigger for a goal that has existed, unused, since Phase 9's own R7 deferred it) and `GET /applications/{id}` (single-resource read for the success-state screen). The `applications` table itself is built to its **full** master-spec shape now (re-migrating a live table later is real cost; the extra columns just sit unused by Phase 10a's own code).

**R11 — `/approvals` scope: no `cancel`.** The master's `POST /approvals/{id}/cancel` is a distinct "abandoned by the user" terminal state. Given R8 already makes `reject` terminal, a separate `cancel` endpoint doing something meaningfully different only matters once notes/audit nuance around *why* an application died is a real product need — a Phase 11 polish item, not required by this phase's bar. Phase 10a ships `GET /approvals?status=pending`, `GET /approvals/{id}`, `POST /approvals/{id} {decision: approve|reject, note?}`.

**R12 — `EmailSender` is `console`-only this phase**, per the roadmap row's own text ("EmailSender console default"). `ConsoleEmailSender.send()` logs the message (structlog) and returns a synthetic `provider_message_id` — no real network I/O, ever, in this phase. SMTP/Resend adapters are a later, explicitly-configured production concern (arguably Phase 14 alongside deployment), not built now. `app/core/config.py` gains `email_provider: str = "console"` as the kill-switch/selector, mirroring the `doc_render_enabled` precedent's spirit (a config flag a later phase extends, not one this phase branches on today — there is exactly one provider).

## 2. New/changed types

`app/domain/agents/blocks.py` — a new `ApprovalActionBlock` field: it already exists (`kind: Literal["approval_action"]`, `approval_id: uuid.UUID`) from Phase 7a — no change needed, it was already correctly shaped for this.

`app/domain/agents/graph.py` — `human_approval` registered via `g.add_node("human_approval", partial(human_approval, deps=deps))` (raw — no `guard()`), exactly like `supervisor`/`halted`.

`app/domain/agents/budget.py` — `guard()` gains `except GraphBubbleUp: raise` before its `except Exception`.

`app/domain/email/types.py` (new) — `EmailMessage(to_email: str, to_name: str | None, subject: str, body: str, body_format: str)`, `EmailSendResult(provider: str, provider_message_id: str)`.
`app/domain/email/sender.py` (new) — `EmailSender` (`Protocol` with `async def send(self, msg: EmailMessage) -> EmailSendResult`), `ConsoleEmailSender` (logs via `structlog`, returns `EmailSendResult(provider="console", provider_message_id=f"console-{uuid.uuid4().hex}")`).
`app/domain/email/factory.py` (new) — `get_email_sender(settings: Settings) -> EmailSender` (returns `ConsoleEmailSender()`; `NotImplementedError` for any other `settings.email_provider` value, mirroring `get_llm_provider`'s own `NotImplementedError` pattern for unbuilt adapters).

`app/domain/agents/graph.py`'s `AgentDeps` — new field `email_sender: EmailSender`.

`app/domain/agents/service.py` — new `AgentService.mark_awaiting_approval(session_id: uuid.UUID) -> None` (sets `status` only, no `ended_at`); new `AgentService.resume_run(user_id, session_id, *, decision: str, note: str | None) -> str` (validates `session.status == "awaiting_approval"`, enqueues `RESUME_JOB` with the SAME `session.run_id`, returns it — does **not** mint a new `run_id` or reset `budget`, since it's continuing the same LangGraph thread).

`app/worker/tasks/agent.py` — `run_agent` (unchanged signature) and a new `resume_agent(ctx: dict, run_id: str, decision: str, note: str | None) -> dict[str, Any]` share a new `_drive(deps, graph, gcfg, s, session, svc, redis, channel, publish, graph_input) -> dict[str, Any]` helper (R5/R6). `WorkerSettings.functions` gains `resume_agent`.

## 3. New tables — migration `0013_applications_approvals`

`app/models/application.py` gains `Application`, `ApprovalRequest` (same module as `CoverLetter`/`ApplicationEmail` — all "application documents/records", consistent with the existing file's scope).

**`applications`** (full master shape, per §5.3): `id` uuid pk · `user_id` FK `users.id` CASCADE not null · `job_id` uuid not null (no FK, mirrors every other job cross-reference in this schema) · `resume_version_id` uuid null (no FK) · `cover_letter_id` uuid null (no FK) · `application_email_id` uuid null (no FK) · `status` String(16) not null server_default `'preparing'` + CHECK `in ('saved','preparing','awaiting_approval','applied','interview','offer','rejected','withdrawn')` · `match_score` numeric(5,2) null · `source` String(16) not null server_default `'mana_ai'` + CHECK `in ('user','mana_ai')` · `ai_session_id` uuid null (no FK — mirrors `ai_actions.entity_id`'s existing loose-reference precedent) · `applied_at` timestamptz null · `last_status_change_at` timestamptz not null server_default `now()` · `notes` Text null · `deleted_at` timestamptz null · `TimestampMixin`. Indexes: `ix_applications_user_status` (`user_id`, `status`), `ix_applications_user_updated` (`user_id`, `updated_at DESC`), `ix_applications_job` (`job_id`).

**`approval_requests`**: `id` uuid pk · `user_id` FK CASCADE not null · `application_id` uuid not null (no FK — the row this snapshot belongs to; no cascade tangle, matches every other cross-reference in this migration) · `ai_session_id` uuid not null (no FK) · `run_id` String(64) not null · `action_type` String(32) not null server_default `'send_application_email'` + CHECK `in ('send_application_email')` (a one-value enum today, matching the master's own single listed action type; widen the CHECK when a second action type exists rather than dropping it now) · `payload_snapshot` JSONB not null `'{}'` · `payload_hash` String(64) not null (sha256 hex digest) · `status` String(16) not null server_default `'pending'` + CHECK `in ('pending','approved','rejected','superseded','expired')` · `decided_by` uuid null (no FK — the approving user; nullable until decided) · `decided_at` timestamptz null · `decision_note` Text null · `expires_at` timestamptz null · `TimestampMixin`. Indexes: `ix_approval_requests_user_status` (`user_id`, `status`), a **partial unique** index `uq_approval_requests_run_pending` on (`run_id`, `action_type`) `WHERE status = 'pending'` (mirrors the master's `partial-unique(run_id, action_type) where status='pending'` exactly — at most one pending approval per run/action-type pair, enforced at the DB level, not just in application code).

Migration: `revision="0013_applications_approvals"`, `down_revision="0012_application_documents"`. Mirror `0011_resume_tailoring.py`/`0012_application_documents.py`'s style exactly. The partial unique index needs `postgresql_where=sa.text("status = 'pending'")` on `op.create_index` — verify this Alembic/SQLAlchemy syntax against the installed version before writing the migration (it is standard SQLAlchemy 2.0 API, but confirm rather than assume, per this project's established habit).

## 4. Nodes

`app/domain/agents/nodes/application_prep.py` (new, `guard()`-wrapped, deterministic — no LLM call) — reads `state["tailored_resume_version_id"]`, `state["cover_letter_id"]`, `state["email_draft_id"]` (all set by the Phase 9 chain this extends) plus `state["inputs"]["job_id"]`; loads the job, cover letter, email rows; builds `payload_snapshot = {"job": {"title", "company"}, "resume_version_id", "cover_letter": {"id", "content"}, "email": {"id", "to_email", "to_name", "subject", "body"}}`; `payload_hash = hashlib.sha256(json.dumps(payload_snapshot, sort_keys=True, default=str).encode()).hexdigest()`; creates one `Application` row (`status="awaiting_approval"`, `source="mana_ai"`, `ai_session_id=deps.session_id`, the three artifact ids) and one `ApprovalRequest` row (`status="pending"`, the snapshot + hash, `run_id=deps.run_id`); back-fills `application_emails.application_id` / `cover_letters.application_id` with the new `Application.id` (both were left `None` when written — this is the one point in the whole system where that forward reference finally resolves); returns `{"application_id": str(app.id), "approval_request_id": str(req.id), "_summary": "Application ready for your review"}`.

`app/domain/agents/nodes/human_approval.py` (new, **raw** per R1/R3) — reads `approval_id = state["approval_request_id"]`; re-reads the `ApprovalRequest` row (harmless on re-execution); calls `decision_payload = interrupt({"approval_id": approval_id})`; on resume, branches on `decision_payload["decision"]`: `"approve"` → `{"approval": decision_payload, "_route": "email_external_action"}`; `"reject"` → `{"status": "rejected", "approval": decision_payload, "_route": "halted"}` (R8); anything else → `{"status": "error", "error": "unrecognized approval decision", "_route": "halted"}` (defensive). Because this node is raw, it must build its own routing key the same way `supervisor` does (`_route`) — `graph.py` needs a dedicated conditional-edge function reading it, not `_halt_or` (which checks `status`, not this node's explicit route).

`app/domain/agents/nodes/email_external_action.py` (new, `guard()`-wrapped) — reads `state["approval_request_id"]`, re-fetches `ApprovalRequest`; asserts `status == "approved"`; recomputes the payload hash from the CURRENT `application_emails`/`cover_letters` rows the same way `application_prep` did and compares to the stored `payload_hash` — mismatch → `{"status": "halted", "error": "approval payload changed since review", ...}` (no send). On match: builds an `EmailMessage` from the current `ApplicationEmail` row, calls `await deps.email_sender.send(msg)`; on success, updates `application_emails.status="sent"`, `.provider`, `.provider_message_id`, `.sent_at`; `applications.status="applied"`, `.applied_at`, `.last_status_change_at`; writes an `audit_logs` row via the existing `app.core.audit.audit()` helper (`actor_type="mana_ai"`, `action="application.email_sent"`, `on_behalf_of_user_id=deps.user_id`, `resource_type="application"`, `resource_id=application.id`); logs an `ai_actions` row (`action_key="sent_application_email"`, `summary=f"Application sent at {sent_at...}"` — matches the master's exact example copy "Application sent at 10:42 AM"); returns `{"status": "completed", "_summary": "Application sent"}`.

`app/domain/agents/nodes/supervisor.py` — unchanged this phase; `prepare_application` already routes to `resume_tailoring` (Phase 9).

`app/domain/agents/nodes/respond.py` — a new branch, checked BEFORE the `email_draft_id` branch: `state.get("application_id")` and `state.get("status") == "completed"` → a "sent" confirmation `TextBlock`. **Not** an `awaiting_approval` branch: tracing the control flow, `respond` is only ever reached via `email_external_action → respond` (a completed send) or a `halted` short-circuit — the worker's own pause-detection (R6, in `_drive()`) returns without re-entering the graph, so `respond` never runs while paused. `ApprovalActionBlock` (already correctly shaped from Phase 7a — `kind`, `approval_id` — no change needed) stays unused by `respond.py` this phase; the SSE `approval` event and `GET /approvals/{id}` already deliver the pending-approval context without needing a response block to carry it.

`app/domain/agents/graph.py` — extend the `email_draft → respond` edge into `email_draft → application_prep → human_approval → {email_external_action | halted}`, `email_external_action → respond`. `human_approval` registered raw; its own conditional-edge function reads `state["_route"]` (not `_halt_or`, since raw nodes emit routing explicitly, matching how `_route_from_supervisor` reads the raw `supervisor` node's `_route`).

## 5. API

`app/api/v1/applications.py` (new router, `prefix="/applications"`): `POST /` `{job_id: uuid}` → 202 `RunRefOut` (reuses the existing `app.api.v1.schemas.ai.RunRefOut{run_id, session_id}` — same shape the résumé-tailor route already returns) — creates an `agent_run` session, `AgentService.start_run(goal="prepare_application", inputs={"job_id": ...})`. `GET /{id}` → `ApplicationOut` (ownership-checked read).

`app/api/v1/approvals.py` (new router, `prefix="/approvals"`): `GET /` `?status=pending` → `ApprovalRequestListOut`. `GET /{id}` → `ApprovalRequestOut` (full `payload_snapshot`). `POST /{id}` body `ApprovalDecisionIn{decision: Literal["approve","reject"], note: str | None}` → **202**: writes the decision onto the `ApprovalRequest` row (`status`, `decided_by=user.id`, `decided_at`, `decision_note`) THEN calls `AgentService.resume_run(...)`, which enqueues `resume_agent`. The route does the decision write itself (not `AgentService`) since it is a plain CRUD update on a row the route already owns via its own ownership check — `AgentService.resume_run` only handles the session/enqueue side.

Both routers registered in whatever central `api/v1/__init__.py`-equivalent wires `resumes.py`/`jobs.py`/etc. today (read that file to match the exact registration call).

## 6. Out of scope (frontend + Phase 11+)

No Builder UI, no approval card, no SSE consumption changes on the frontend (Phase 10b). No `applications` list/patch/notes/timeline endpoints, no Kanban (Phase 11). No reject→revise loop (R8). No edits/reconfirm flow (R9). No `cancel` endpoint (R11). No SMTP/Resend `EmailSender` adapters (R12) — `email_provider` other than `"console"` raises `NotImplementedError`, matching `get_llm_provider`'s existing pattern for an unbuilt adapter.
