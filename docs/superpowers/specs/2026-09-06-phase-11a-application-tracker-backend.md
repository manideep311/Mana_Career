# Phase 11a — Application tracker (backend) design addendum

> Delta over master `2026-08-30-mana-career-design.md` §5.3 / §6.2 (`/applications`) / §9 (roadmap row 11). Phase 10 shipped `POST /applications` (prepare) + `GET /applications/{id}` + the `applications` / `approval_requests` tables. This phase adds the rest of the `/applications` resource that the Kanban tracker (Phase 11b) needs: list, status change (with an audit trail), notes, timeline, soft-delete, and the `intent=save` path.

## 0. Goal (roadmap row 11, backend half)

Everything Phase 11b's Kanban + application-detail page reads or mutates: `GET /applications?status=&sort=`, `PATCH /applications/{id}` (a column drag → a persisted status change + an `application_events` row + an `audit_logs` row), `POST /applications/{id}/notes`, `GET /applications/{id}/timeline` (merged `application_events` + `ai_actions`), `DELETE /applications/{id}` (soft), and `POST /applications` gaining `intent: save` (add a job to the pipeline with no agent run).

## 1. Rulings

**R1 — `application_events` is the one remaining supporting table.** Migration `0014_application_events`, per §5.3: `id · application_id (FK `applications.id` CASCADE) · user_id (FK `users.id` CASCADE) · kind CHECK `in ('status_change','note','interview_scheduled','ai_action','email_sent')` · from_status String(20) null · to_status String(20) null · body Text null · meta JSONB not null `'{}'` · occurred_at timestamptz not null server_default `now()``. Indexes: `ix_application_events_app` (`application_id`, `occurred_at DESC`), `ix_application_events_user` (`user_id`). **No `updated_at` trigger** — append-only, `created_at` only via a plain column (mirror `agent_steps` / `ai_actions`, which are also append-only and use `TimestampMixin` — actually those DO carry `updated_at`; `application_events` is closer to `audit_logs`, which has only `created_at`). Ruling: `application_events` carries **only `created_at`** (a plain column, no `TimestampMixin`, no trigger) plus its own `occurred_at`, matching `audit_logs`' append-only shape.

**R2 — a real `ApplicationService`.** The `app/domain/applications/` package does not exist yet (Phase 10a's nodes wrote `Application` rows via raw `session.add`). This phase creates `app/domain/applications/service.py` with `ApplicationService(session)` — `list_`, `get`, `patch`, `add_note`, `timeline`, `soft_delete`. It is a `domain`-layer leaf: may import `app.core.*` (incl. `app.core.audit.audit`), `app.models.*`; must NOT import `api`/`worker`/sibling business domains. **No new import-linter contract** — `lint-imports` stays `3 kept, 0 broken` (the existing "layered architecture" contract already permits a new `domain` package).

**R3 — user-settable status is a strict subset.** `applications.status`'s CHECK (migration `0013`, widened to `String(20)`) allows `saved, preparing, awaiting_approval, applied, interview, offer, rejected, withdrawn`. `preparing` and `awaiting_approval` are agent-run-internal — `PATCH` must reject them. `ApplicationPatchIn.status` is `Literal["saved", "applied", "interview", "offer", "rejected", "withdrawn"] | None`. A status change also: writes an `application_events` row (`kind="status_change"`, `from_status`, `to_status`), calls `audit()` (`actor_type="user"`, `action="application.status_change"`, `actor_user_id=user.id`, `resource_type="application"`, `resource_id=id`, `meta={"from": …, "to": …}`), sets `last_status_change_at = now()`, and sets `applied_at = now()` iff the new status is `applied` and `applied_at` was null. `notes` in the same PATCH is a plain field update (no event).

**R4 — `POST /applications` returns a union.** `ApplicationCreateIn` gains `intent: Literal["prepare", "save"] = "prepare"`. `prepare` → unchanged (202, `RunRefOut`). `save` → create an `Application` row directly (`status="saved"`, `source="user"`, the given `job_id`, everything else default/null), write an `application_events` row (`kind="status_change"`, `from_status=None`, `to_status="saved"`) + an `audit()` row, commit, return **201 `ApplicationOut`**. The route's return type is `RunRefOut | ApplicationOut` and its `status_code` is set per-branch via `Response.status_code` (or two `@router.post` handlers is messier — use one handler, `response.status_code = 201` in the save branch). FastAPI serialises a `Union` response fine.

**R5 — the timeline merges two sources, read-only, newest-first.** `ApplicationService.timeline(user_id, application_id)` returns `list[TimelineItem]` where `TimelineItem = {kind: str, at: datetime, title: str, detail: dict}`. Sources: (a) every `application_events` row for the application (`kind` → itself; `title` derived — `status_change` → `"Moved to {to_status}"`, `note` → `"Note added"`, etc.; `detail` = `{from, to, body, ...}` non-null subset); (b) every `ai_actions` row where `ai_session_id == application.ai_session_id` (only when the application has one — a `save`-intent application has `ai_session_id=None`, so no ai_actions) mapped to `{kind: "ai_action", at: occurred_at, title: summary, detail: dict(detail)}`. Merge, sort by `at` descending. No pagination this phase (an application's history is small).

**R6 — soft-delete only.** `DELETE /applications/{id}` sets `deleted_at = now()`, returns 204. Every `ApplicationService` read (`list_`, `get`, `timeline`) filters `deleted_at IS NULL`. No hard delete anywhere (matches the "nothing user-visible is destroyed" §7.5 rule).

**R7 — list sort + filter.** `GET /applications?status=<one of the 8>&sort=<recent|status>`: `status` optional exact-match; `sort` defaults to `recent` (`updated_at DESC`), `status` orders by a fixed pipeline rank (`saved < preparing < awaiting_approval < applied < interview < offer < rejected < withdrawn`) then `updated_at DESC`. No cursor pagination this phase — an early user has few applications; a `limit`/`offset` pair with a sane default (`limit=100`) is enough and matches how `/resumes`/`/jobs` list endpoints already work in this codebase (check one and mirror its pagination shape).

## 2. API surface (all under `app/api/v1/applications.py`, extending the Phase 10a file)

- `POST /applications` — `ApplicationCreateIn{job_id, intent="prepare"}` → **202 `RunRefOut`** (prepare) or **201 `ApplicationOut`** (save). (R4)
- `GET /applications` — `?status=&sort=&limit=&offset=` → `ApplicationListOut{items: ApplicationOut[], total: int}`. (R7)
- `GET /applications/{id}` — unchanged (Phase 10a).
- `PATCH /applications/{id}` — `ApplicationPatchIn{status?, notes?}` (`extra="forbid"`) → `ApplicationOut`. (R3)
- `POST /applications/{id}/notes` — `ApplicationNoteIn{body: str}` (1–4000 chars) → **201 `TimelineItemOut`** (the created note event). Writes an `application_events` row `kind="note"`.
- `GET /applications/{id}/timeline` — → `ApplicationTimelineOut{items: TimelineItemOut[]}`. (R5)
- `DELETE /applications/{id}` — → **204**. (R6)

Schemas in `app/api/v1/schemas/applications.py` (extend the Phase 10a file): `ApplicationListOut`, `ApplicationPatchIn`, `ApplicationNoteIn`, `TimelineItemOut{kind: str, at: datetime, title: str, detail: dict[str, Any]}`, `ApplicationTimelineOut`. `ApplicationOut` gains `notes: str | None` and `ai_session_id: uuid.UUID | None` (both already columns; the current `ApplicationOut` just doesn't expose them — add them, the Phase 11b detail view wants `notes`).

`ApplicationService` is constructed in the routes the same way `TailoringService`/`ResumeService` are (`ApplicationService(db)`), does its own `user_id` ownership filtering (→ `NotFoundError` on miss), and does NOT commit — the request session autocommits when the handler returns (the established `get_session` dependency pattern; `POST …/save` is the exception that needs an explicit `db.commit()` because it currently mirrors the Phase 10a `prepare` branch which commits).

## 3. Out of scope

Phase 11b (the Kanban board, the detail page, drag-and-drop, the nav entry, optimistic UI). `interview_scheduled` as a distinct user action / "log interview" form — the `kind` value exists in the enum but this phase writes only `status_change`, `note`, and (via the agents, already) nothing else; a dedicated "log an interview" endpoint is a later polish. Cursor pagination. `application_events` for the `email_sent` kind (Phase 10a's `email_external_action` already writes an `audit_logs` row + an `ai_actions` row on send — the timeline picks the `ai_actions` one up via R5(b); a redundant `application_events` row is not added).
